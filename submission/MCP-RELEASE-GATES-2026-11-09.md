## 已确认的两件事

### TikTok 游客设备注册与已声明范围冲突

`scripts/remote-capabilities.mjs` 的现有精确排除表已排除 Douyin 设备注册、游客凭证获取及广告主会话身份，却遗漏 `data:tiktok.web.device_register`。完整 988 工具快照仍包含这项工具，展示说明也明确其用于游客设备 ID/Cookie，而不是社媒内容调研。

`submission/SUBMISSION.md` 声明公开范围排除设备注册/游客凭证；当前遗漏与该声明存在确定的一致性问题。另以纯占位数据测试现有通用结果 renderer，cookie 字段仍被保留，说明不能把通用脱敏器当作这项范围规则已经执行。没有使用真实 Cookie，也没有执行真实设备注册；该离线证据不等于证明生产曾泄露凭证，更不等于已认定这类工具必然违反某条 OpenAI 政策。

建议仅从公开 ChatGPT 目录排除这项工具，保留原 API、本地 MCP 和其他宿主能力。因为用户此前要求保留全部能力，本轮**没有擅自修改排除表或移除工具**。

### BeatAPI 账户授权不等于 Bilibili 广告主授权

已读取的本地链路：

1. `router/beatapi-mcp-executor.go` 的授权上下文把 MCP grant 绑定到 BeatAPI 用户、钱包与连接限额。
2. `relay/channel/task/jsplugin/adaptor.go` 从选中渠道凭证设置插件 apiKey。
3. 插件的人群包请求只有 GET 路径、通用授权头和空参数，没有调用方可选的 Bilibili 广告主账号输入。

用同一虚拟渠道配置和两个不同的模拟用户 ID 调用纯请求构造函数，得到完全相同的请求。它只证明这个插件阶段不会根据模拟用户 ID 自动选择广告主；**不证明生产所有用户使用同一渠道，也不证明越权**。渠道分配、数据方服务许可和委托授权可能另有合法安排，当前没有运行侧证据。

因此仍需确认：实际广告主/资源域是谁、是否授权此服务向用户提供这些包、是否存在跨租户数据隔离要求。不能仅凭已登录 BeatAPI、钱包扣费成功或元数据扫描无反馈断言已完成这层授权。

## 推荐决策

为避免改动现有 API 或临时设计另一套广告主授权，建议：

- TikTok 游客设备注册：仅从公开 ChatGPT 目录排除。
- Bilibili 自定义人群包列表：在拿到授权归属与可展示范围证据前，暂不放入公开 ChatGPT 目录。
- 两项原有 API 和本地工具保留；其余能力及参数约束不变。实施后公开目录数量会变化，不能继续把新的送审候选称为完整 988 工具。

这是一项待用户确认的**公开产品范围决策**，不是已实施修复。若选择保留人群包，提供非敏感的资源归属/委托说明即可，不要把渠道 Key、Cookie、个人名单或密码放进聊天或仓库。若选择保留设备注册，则需重新明确公开范围、合理用途、结果披露与安全边界，不能只换个标题绕过问题。
